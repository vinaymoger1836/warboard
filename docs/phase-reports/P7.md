# P7 — Operations planner, after-action reports and replay: phase report

Date: 9 Nov 2026. Status: **done locally; CI not yet run** (every check below ran on the working tree on 9 Nov 2026, Windows 11, Rust 1.99, Node 24). Nothing is committed (CLAUDE.md rule 10).

## What was built

| Area | Result |
|---|---|
| Operation model (`wb-sim/src/operations.rs`, ADR-043) | An operation is phases with tasks, a trigger, an end condition (default: all tasks done) and optional abort conditions. One condition tree for all three: `all` / `any` over leaves `start` (H + delay), `at_time`, `phase_started` / `phase_ended` (+ delay), `manual`, `contacts` (count, domain, level, area; side picture only), `intel_report`, and phase-only `arrived`, `tasks_done`, `weapons_done`, `targets_destroyed`, `elapsed`, `losses_pct`, `bingo`, `under_attack`, `fuel_below`. States: operation planned / running / paused / completed / aborted; phase waiting / running / done / aborted / cancelled. |
| Evaluation | New `operations` stage right after `orders`. Per running operation it starts, ends, aborts and cancels phases until nothing changes, so "with phase X" starts on the same tick. Phase tallies (launched, hits, intercepted, decoyed, jammed, lost, in flight, bingo, under attack) come from the side's own events. Aborting sends a phase's aircraft home and stops its ships. |
| Commands | `CreateOperation` (spec, `replace`, `start`; id = the order's `seq`), `StartOperation`, `PauseOperation`, `ResumeOperation`, `AbortOperation`, `PhaseGo`, `EndPhase`, `EndWar`. Logged and replayed like every order. |
| DAG and planner validation | Refused: unknown phase ids, trigger cycles (named, e.g. "Phase 1 → Phase 2 → Phase 1 wait for each other"), phase-only leaves in a trigger, bad delays and percentages, every task check of `AssignTask`. Flagged (`operations::check`, live in the planner): units busy in a running operation, rounds carried vs wanted and base stock, fuel to the furthest task point and back (a tanker on the side or in the plan turns it into a note), strikes on contacts not identified hostile (the operation approves them), patrols under ROE Charlie, a unit tasked in several phases. |
| Fire missions (ADR-043) | A phase task with `fire: true` adds a mission to the group (`Group.fires`) instead of replacing its task; the engage stage fires it like a strike, pre-approved, from where the group is. This is how one frigate fires at both corvettes on the same tick while it keeps its patrol (doc 03 §8.1 phases 3–5). |
| Planned targets | `near_km` on a strike at a point: at phase start the strike is aimed at the side's nearest non-friendly contact within the radius; the operation approves that designated target only (doc 03 §7). |
| Reports (`wb-sim/src/reports.rs`) | Totals, intel log, salvo reports (one line per salvo in the doc 03 §12 form plus each weapon's outcome and endgame factors), losses (platform and cause), our hits, munitions (expended, on units, in stock, by base), sorties (take-off, landing, fuel left, refuels, bingo, rounds fired, loadout), operation report (per phase: start, end, why, tasks, tally). Built only from the side's events and own state. After `EndWar`, the truth review: both sides' forces and losses, every hit (truth-only `TruthHit` events, side mask 0), and each contact against what it really was, with the position error. Export: JSON, one CSV per table (10 tables), printable HTML; the same Rust code serves `wb report` and the browser. |
| Replay (`wb-sim/src/replay.rs`) | A checkpoint every 10 sim minutes (zstd snapshot, state hash, event count), at most 144 (older half thinned), saved with the war. `Replay` is a second sim: seek restores the nearest earlier checkpoint, cuts the event log back and re-simulates, re-queueing each logged order on the tick it was submitted (`QueuedOrder::submitted`, new). |
| CLI | `wb report` (JSON, CSV, HTML; `--truth` ends the war first), `wb replay` (verifies every checkpoint, `--seek` compares arbitrary ticks with the original run). Golden metrics `phase_start_gap_ticks`, `phase_start_s`, `phases_ended`, `phases_done`, `operation_completed`. Benchmarks and goldens run without checkpoints. |
| Browser | Operations tab in the dock (operation list, SVG timeline with bars in `side.own`, running phase outlined amber, aborted in `state.bad`, waiting and cancelled dashed, trigger arrows; phase rows with trigger, end, abort, tasks, results; START / PAUSE / RESUME / ABORT with an inline confirm; GO for manual phases, END for running ones). Planner panel (phases, tasks for the selected group, routes and orbits drawn with the map tools, targets picked on the map, weapon, rounds, fire mission, search radius, trigger / end / abort builders, live engine findings, CREATE and CREATE AND START). Phase routes on the map (amber routes with `P3 WP 1` labels, dashed orbits, `P4 TARGET`). Reports panel (REPORTS in the top bar) with the exports and END WAR. Replay bar (REPLAY in the top bar) with a scrubber, checkpoint marks, ±10 min, EXIT REPLAY; the war pauses meanwhile. Event log lines for operation, phase and war events. |
| Scenario | `scenarios/golden/rising-sun.yaml` = G13 on the generic fixtures in the test sea area: ESM aircraft recon (phase 1), two stand-off jammers (2), frigate to a patrol box (3), two fire missions of 3 test ASMs each at the two corvettes (4, 5 with 4), two fighters with 4 test ARMs at the SAM site (6, phase 2 started + 10 min). |

## Found while completing the phase

1. **ESM fixes were wrong by 100–200 km and never improved (P4 defect).** `bearing_fix` chose the bearing pair with the *widest crossing angle*. With up to 16 bearings taken while an aircraft flies almost straight at the emitters, that pair is the noisiest one, and the fix landed 215 km from the SAM site with a 6 km ellipse. The estimate was then only replaced once its ellipse grew past 50 km, which a fixed site never does. Now the pair is the one whose origins lie furthest apart *across* the line of bearing (geometry that noise does not change), it must still cross at `esm_fix_min_angle`, and a later fix replaces the estimate when its ellipse is smaller. In Rising Sun the SAM site's estimate is now within about 2 km of the truth by T+0:40. No golden band moved (G4 measures first detection).
2. **Strikes on a point ignored launch doctrine.** The point-strike path always fired at maximum range. It now uses the doctrine range against a still target; for `max_range` and `no_escape_zone` that is the same value, so G10 and G12 are unchanged. Rising Sun's fighters use `close` (half range).
3. **Test ARMs fired at the flyout table's maximum range ran out of energy short of it** (launched at 44.5 km, out of energy after 32 km at 8–9 km altitude). Not changed (weapon balance, P5/P6b): Rising Sun works around it with the `close` doctrine. Worth a look in P8's test bench.
4. **An operation's first phase "finished" before its aircraft took off.** A group still at base counted as home again. Tasks now count as home only once their group has been away since the phase started.

## Decisions and deviations

- **ADR-043 (Proposed)** covers the condition tree, evaluation and cancellation, fire missions, planned targets (`near_km`), operation ids, planner validation, truth-only events and replay checkpoints. Please confirm, in particular:
  - **Fire missions** as a second kind of phase task (doc 03 §8.1 needs one ship on two strikes at once);
  - **cancelled** phases (a trigger that waits for an aborted or cancelled phase can never fire) and an operation that **completes** when every phase is final;
  - **`TruthHit` with side mask 0** in the shared event log, rather than a separate truth log.
- **Phase 2 of Rising Sun** ends "manual or bingo **or after phase 6**". Doc 03 says "manual or bingo"; the golden cannot press END (scenario orders are checked at tick 0, before the phase runs), and the jammers carry 8 hours of fuel.
- **"Detected before H-hour"** (doc 03 §8 abort example) is not a leaf: a side does not know when it has been detected. `under_attack` (a weapon seen coming at a member) is the nearest thing the side does know.
- **"Objective destroyed"** is `targets_destroyed`: the designated contacts have left the side's picture. Today contacts leave the picture when their unit is destroyed (`picture::forget`), so this tells the side about kills it may not have seen; a later phase could make it a battle-damage assessment.
- **Report cause of loss** is from the side's own knowledge: shot down, sunk or destroyed by domain, not the weapon that did it.
- **UI decisions not in doc 10:** Operations, Reports and Replay use existing tokens (`side.own` bars, `btn.border` amber outlines, `state.bad` aborts, `weapon.offensive` routes); REPORTS and REPLAY sit in the top bar beside SAVES and PACKS. If you want them elsewhere, say where.
